# AUDIT-2026-08-18.md — Independent astronomy/engineering audit of the pipeline

Conducted 2026-08-18 by reviewing the actual code of all seven core subsystems (FITS
headers/normalizer/QC, `modules/astrometry/`, photometry + forced photometry,
`modules/subtraction.py`, `modules/catalog_matcher/`, `modules/anomaly_detector/`, and
`pipeline.py`/`worker.py`/`watcher.py` orchestration) against astronomical/astrometric
correctness — not just against what CLAUDE.md claims. The most significant findings below
were additionally spot-checked directly against the source before being written up here.

Already-tracked open items (`docs/ISSUES.md`, and the "Known Issues" section of CLAUDE.md —
faint `UNKNOWN`, `0 calibrated` frames, orphaned finder charts, density-dependent WCS-offset
failure) are **not** repeated here. Only findings not previously documented as an open
question are listed.

**Totals:** 12 critical, 19 high, 16 medium, 7 low findings, plus 7 items that looked
suspicious going in but were verified correct.

Severity guide used below:
- **Critical** — a mechanism that can silently drop a real anomaly, or silently corrupt data
  for a whole class of frames, with no distinguishing log line.
- **High** — systematic (not random) distortion or loss, but narrower in scope than Critical.
- **Medium** — real, but triggered by a specific, less common condition.
- **Low** — worth knowing/fixing, but not currently causing systematic data loss.

A finding headed **✅ DONE** has been addressed on the `develop` branch; the note under its
heading records what was changed and in which commit. A finding headed **→ observatory-api**
cannot be fixed from this repository and has been queued in
[API-TASKS.md](API-TASKS.md) instead.

## Critical findings

### ✅ DONE — C1. Δmag-based classification (VARIABLE_STAR / BINARY_STAR / brightening SUPERNOVA_CANDIDATE) is effectively unreachable outside Simbad-matched objects

**Location:** `modules/anomaly_detector/_classify.py:434-513`, `modules/catalog_matcher/_gaia.py:163`, `_2mass.py:138`, `_panstarrs.py:124`

All three branches past the `DELTA_MAG_ALERT` threshold gate on `object_type` via
`_is_variable_star`/`_is_binary_star`/`_is_galaxy` — substring checks against Simbad OTYPE
codes. But `_gaia.py`, `_2mass.py`, and `_panstarrs.py` all hardcode
`source["object_type"] = "STAR"` for any match — a generic label, not a Simbad OTYPE, and none
of the three classifiers ever match on it. Only `_simbad.py` writes a real OTYPE.

**Scenario:** a star known only through Gaia DR3 (the overwhelming majority of any field)
genuinely changes brightness by 2-3 mag between epochs — a dwarf-nova outburst, a previously
unknown variable. `delta_mag` is computed correctly and clears the threshold, but no branch
fires.

**Consequence:** the anomaly is silently dropped (`return None`), no warning logged. In
practice the Δmag detector can only confirm variability the catalog already knew about; it
cannot discover anything new — directly contrary to the module's stated purpose.

**Fix direction:** derive "was this source previously stable" from its own historical
magnitude scatter, independent of Simbad OTYPE, rather than gating entirely on catalog type.

**Fixed.** `modules/anomaly_detector/_history.py` gained `_history_mag_scatter()` — a
MAD-derived 1σ equivalent of the source's own same-filter magnitudes (MAD rather than RMS
so a single bad epoch can't inflate the baseline enough to mask the change it calibrates).
`_classify.py` gained a final, catalog-independent `VARIABLE_STAR` branch below the three
OTYPE-gated ones: a source whose own same-filter history spans at least
`VARIABILITY_MIN_EPOCHS` (3) epochs and whose `delta_mag` exceeds `VARIABILITY_SIGMA` (3.0)
times that history's scatter is reported regardless of what the catalogs call it, with the
`notes` field stating the classification came from the light curve. Screening on the source's
own scatter rather than a flat threshold keeps intrinsically noisy sources quiet;
`DELTA_MAG_ALERT` still applies as an absolute floor. The `anomaly_type` stays `VARIABLE_STAR`
rather than a new enum member, since that enum is mirrored as an `ENUM` column constraint in
observatory-api.

### ✅ DONE — C2. Hard `elongation < 5.0` cutoff in extraction makes `SPACE_DEBRIS_EDGE_ELONGATION_MIN=6.0` dead code

**Location:** `modules/astrometry/_extraction.py:277`, `config.py:245`

```python
mask_all = mask_fwhm_min & (elongations < 5.0) & mask_flux
```

This hardcoded (not `config.py`-driven) bound gates the loose `sources_all` list — the only
feed `catalog_matcher`/`anomaly_detector` get for non-strict detections. But
`anomaly_detector` expects edge-of-frame sources with elongation up to **6.0** (coma near the
edge produces less-elongated shapes than a genuine trail, hence the raised edge threshold).

**Scenario:** a debris fragment/satellite/fast NEO near the frame edge with elongation in
[5.0, 6.0) or higher — exactly the case the raised edge threshold exists for.

**Consequence:** the source is cut at extraction time; `anomaly_detector.py` never sees it —
not as `SPACE_DEBRIS`, not even as `UNKNOWN`. The edge-elongation branch cannot fire in
practice.

**Fix direction:** raise the cutoff to at least `config.SPACE_DEBRIS_EDGE_ELONGATION_MIN` (and
move the constant into `config.py`).

**Fixed.** The constant became `config.SOURCES_ALL_ELONGATION_MAX`, default `15.0` — above
`SPACE_DEBRIS_EDGE_ELONGATION_MIN` (6.0) with room for a genuinely short trail, whose `a/b`
ratio scales with how narrow the frame's PSF is. Anything both highly elongated *and* longer
than `STREAK_MIN_LENGTH_ARCSEC` is already removed by the streak pre-pass before extraction,
so what this bound sees is a sub-30″ trail — a fast NEO or a short debris streak. It still
rejects the degenerate ratios a near-zero minor axis produces (`_extraction.py` clamps `b` to
`1e-6`, see L4). Since the dead state is reachable again by configuration,
`_extraction.py` logs a warning whenever the ceiling is not above
`SPACE_DEBRIS_EDGE_ELONGATION_MIN`.

### ✅ DONE — C3. Sequential exclusive catalog matching leaves MPC the last, narrowest chance

**Location:** `modules/catalog_matcher/_match.py:157-207`, `_mpc.py:183`

Order is Simbad → Gaia → 2MASS → Pan-STARRS → MPC, each stage seeing only sources not already
claimed (`catalog_name is None`) by an earlier one. MPC only gets what nothing else claimed
within `MATCH_CONE_ARCSEC=5"` across four prior passes.

**Scenario:** an asteroid/NEO happens to project within 5" of a background Gaia star or Simbad
object (routine in dense fields/near the galactic plane) — it is permanently tagged
`"Gaia DR3"`/`"Simbad"` before SkyBot ever gets a look.

**Consequence:** loss of `ASTEROID`/`COMET` classification and ephemeris; the blended flux
(star + overlapping object) can even produce a false "brightening" → false `VARIABLE_STAR`/
`SUPERNOVA_CANDIDATE` instead of the real moving object.

**Fix direction:** run the MPC/SkyBot check against all sources concurrently (not only the
unclaimed remainder), and resolve conflicts with an explicit priority rule instead of catalog
order.

**Fixed** as directed, in `_mpc._match_mpc()` alone — the stage keeps its position last in
`_match.py`, it is only its candidate pool that widened to every source. The explicit priority
rule is positional:

* A source already claimed by a stellar catalog is taken over **only** when the ephemeris
  position falls within the tight `MATCH_CONE_ARCSEC` of it — the blend this finding describes.
  The wide `MOVING_CONE_ARCSEC` (120") is deliberately *not* allowed to trigger a takeover: at
  that radius some catalogued star is almost always present whether or not it has anything to do
  with the moving object, so using it would trade this false negative for a much more common
  false positive.
* Beyond that tight cone, the MPC object falls back to the nearest *unclaimed* source within
  `MOVING_CONE_ARCSEC` — the previous behaviour, unchanged.

Both halves of the finding are covered: the blended detection now wins the designation, and the
unrelated bystander that used to receive it (producing a false stationary "asteroid") stays
uncatalogued. One-to-one assignment and nearest-first conflict resolution between competing MPC
objects are preserved; the ordering key is now whichever separation actually applied to each
proposal. A takeover is logged at INFO with both identities, since it is the only place in
catalog matching where an already-assigned identity changes.

Deliberately reuses `MATCH_CONE_ARCSEC` rather than adding a separate knob — the rule *is*
"as tight as ordinary stellar cross-matching", and a deployment that retunes that cone should
retune this with it.

### ✅ DONE — C4. No EXPTIME/GAIN flux normalization before median-stacking reference frames

**Location:** `modules/subtraction.py:950-951` (median stack → diff)

Reference frames are median-stacked and subtracted in raw ADU with no common flux-scale
normalization. An object's archive can easily contain frames with different exposure times/gain
(auto-exposure, different sessions).

**Scenario:** new frame at 120s, archive only has 60s frames (or a different gain) — for a
star with constant flux, the post-subtraction residual is ~(K−1)×flux_star at the position of
**every** star in the frame, where K is the scale mismatch.

**Consequence:** mass false candidates across the whole frame (potentially hundreds of false
`UNKNOWN`/`SPACE_DEBRIS`), plus elevated background noise masking genuine faint transients.

**Fix direction:** scale each reference by `exptime_new/exptime_ref` (and gain, if it differs)
before stacking.

**Fixed** as directed. `_read_flux_scale_keys()` reads `EXPTIME`/`EXPOSURE` and the sensor gain
from a frame's headers, and `_flux_scale_factor()` turns them into the multiplier
`(t_new / t_ref) × (g_ref / g_new)` — a frame's ADU scale as `exposure / gain(e⁻/ADU)`, so the
gain ratio is inverted relative to the exposure one. Each of the two factors independently falls
back to `1.0` when its keyword is missing on either side: an archive with no `EXPTIME` at all
behaves exactly as it did before, rather than losing subtraction outright. `EGAIN` is preferred
over `GAIN` for the same reason as in C7, and `PHOTOMETRY_GAIN_E_PER_ADU` deliberately does not
override the header here — a deployment-wide value is identical on both sides and cancels in the
ratio, so honouring it could only mask a genuine per-frame difference.

Two details worth recording:

* The factors are applied to the **median stack**, not to the aligned reference arrays
  themselves. `_build_saturation_mask()` compares those against `SATURATION_ADU`, and a
  reference scaled down (a 300″ reference against a 60″ frame is ×0.2) would otherwise drop its
  saturated core below that threshold and escape masking — trading this finding for a
  reintroduction of docs/ISSUES.md #1/#2.
* Scaling raw ADU also scales the reference's bias/sky pedestal, leaving a smooth
  `(K−1) × pedestal` term in the difference image. That one is harmless: it is removed by
  `_detect_diff_sources()`'s own `sep.Background()` pass, unlike the per-star residual this
  change cancels, which is not smooth and is exactly what SEP would otherwise report.

The new frame itself is never rescaled — its pixel values are what candidate fluxes and the
`SATURATION_ADU` checks are measured in. A mixed archive still costs sensitivity (scaling a
short reference up amplifies its noise), so a reference needing more than a 2× correction in
either direction is reported at WARNING with the worst factor, and a new frame with no usable
`EXPTIME` at all is reported once per frame.

Reference *selection* remains untouched here — the filter-token collision that decides which
frames get stacked in the first place is C5 below.

### ✅ DONE — C5. Filename-token collision between the FrameType code and the Filter code in reference selection

**Location:** `modules/subtraction.py:118-125`

Filename format is `{Object}_{FrameType}_{Filter}_{Exptime}_{DateTime}`, with FrameType codes
L=Light, D=Dark, F=Flat, B=Bias. Reference selection searches for the substring
`"_{filter}_"`. But **every** Light frame contains `_L_` right after the object name (the
FrameType code, not the filter) — with `filter_name="L"` (Luminance) this matches any Light
frame regardless of its actual filter (e.g. Ha or OIII). Similarly the Bias FrameType code `B`
collides with the Blue filter code `B`.

**Scenario:** an object shot in Luminance; the same night's archive also holds an LRGB
sequence plus calibration frames — the "same filter" search returns a mix of L/Ha/OIII frames
and/or Bias frames.

**Consequence:** mixing filters/calibration frames into the reference stack compounds C4 even
further (the L vs. Ha difference is enormous); starless calibration frames can crowd out real
science references from the top-`_MAX_FRAMES` selection.

**Fix direction:** match against the positional filename field (parse by delimiter, not
substring), and explicitly exclude Dark/Flat/Bias by FrameType code.

**Fixed** as directed, with one correction to the finding as written: the FrameType field is no
longer a one-letter code. `modules/normalizer.py` writes the full word (`Light`/`Dark`/`Flat`/
`Bias`), so the literal `_L_` vs. Luminance collision described above belongs to the earlier
filename revision rather than to today's archive. What is live today is the second half — the
pipeline archives calibration frames into the **same** per-object directory as the science
frames, and nothing in reference selection ever looked at the frame type, so a starless
Dark/Flat/Bias was a perfectly eligible reference and, being recent, would crowd real science
frames out of the newest-first `_MAX_FRAMES` selection. An archive that still holds
older-revision filenames has the collision too.

`_parse_normalized_filename()` reads the frame type and filter positionally. The fields are
anchored on the **DateTime** token — the one field with a distinctive shape — and counted
leftward from it, rather than from the left, because the object name may itself contain
underscores (`Andromeda_Galaxy`, `4_Vesta`) and the sequence suffix is optional. That also
disambiguates the legacy codes for free, so such an archive parses correctly rather than being
rejected: `L` in the FrameType position is Light, `L` in the filter position is Luminance
(`M51_L_L_120_<dt>` resolves the way it was written).

Calibration frames are then dropped before any filter logic runs, and the same-filter test
compares against the parsed filter *field* instead of searching the whole basename for a
substring. A filename that doesn't follow the convention at all (`NORMALIZE_ENABLED=false`, or
a file placed in the archive by hand) is deliberately left alone on both counts: it keeps the
old substring filter test, and is never excluded as calibration, since it cannot be identified
either way and such a deployment must not lose subtraction over it.

### ✅ DONE — C6. Step 4.6 deduplication unconditionally drops uncatalogued sources near any catalogued star — including confirmed subtraction candidates

**Location:** `pipeline.py:1485-1540` (`_dedupe_unmatched_near_matched`), called from
`pipeline.py:525`

The function discards any uncatalogued source within `MATCH_CONE_ARCSEC` (5") of an arbitrary
catalogued star in the same frame, with no exemption for sources carrying
`_from_subtraction=True` — i.e. already confirmed as a real pixel-level change by an
independent, catalog-agnostic method.

**Scenario:** a supernova/nova flares up in projection within 5" of a catalogued star
(realistic in a dense field, or near a known galaxy/companion star) — `subtraction.run()` has
already confirmed the pixel-level change, but Step 4.6 sees "uncatalogued source near a star"
and silently drops it.

**Consequence:** a real anomaly (`SUPERNOVA_CANDIDATE`/subtraction-sourced `UNKNOWN`)
disappears before `anomaly_detector.py` and before `POST /frames/{id}/sources` — the event is
never stored in any form.

**Fix direction:** exempt `_from_subtraction=True` sources from this dedup step — pixel-level
confirmation outweighs the deblending-artifact risk the step exists to guard against.

**Fixed** exactly as directed. The artifact the step guards against is a *deblending* one —
sep splitting one distorted PSF into two components within this frame's own pixels — whereas a
subtraction candidate carries evidence of a different kind: a confirmed pixel-level change
against a median stack of the object's own archived history, established without consulting
any catalog. The exemption is logged separately from the suppression count so the two remain
distinguishable in a frame's log.

Registration residuals around bright stars, the obvious worry with this exemption, are already
handled upstream in `modules/subtraction.py` rather than here: it masks everything within
`SATURATION_MASK_RADIUS_ARCSEC` (10″, wider than `MATCH_CONE_ARCSEC`'s 5″) of any saturated
pixel in the new frame or any aligned reference, and rejects `near_edge` candidates outright,
so such a residual never reaches step 4.6 to begin with.

Note: step 4.6 itself is still absent from CLAUDE.md's pipeline step list — that is L7 below,
which will document this exemption along with the step.

### ✅ DONE — C7. GAIN (e⁻/ADU) is extracted from the header but never used in the flux-error formula

**Location:** `modules/photometry.py:442-444`, `modules/forced_photometry.py:160`

```python
flux_err = sqrt(abs(net_flux) + ap_area * sky_sigma ** 2)
```

The Poisson term treats `net_flux` (in ADU) directly as the variance, which is only correct at
gain=1 e⁻/ADU. Real cameras almost never have gain=1 (CCD ~0.5-2 e⁻/ADU; CMOS anywhere from
&lt;1 to several).

**Scenario:** any frame with gain≠1 — i.e. almost any real frame.

**Consequence:** at gain&gt;1, `flux_err` is overstated → `snr` understated →
`forced_photometry.py` systematically fails real faint objects against
`FORCED_PHOTOMETRY_MIN_SNR` and silently loses them (defeating the entire point of precovery).
At gain&lt;1, the reverse: noise is reported as a significant detection.

**Fix direction:** thread `gain` into `photometry.measure()`/`forced_photometry.run()` and
divide the Poisson term by it: `net_flux/gain + ap_area*sky_sigma**2`.

**Fixed,** with one deliberate deviation from the direction as written. The formula is now
`sqrt(|net_flux| / gain + ap_area * sky_sigma**2)` in both modules, and both gained an optional
`gain=` parameter — but `pipeline.py` does **not** pass one, and the header value is resolved
inside each module instead.

The reason is the keyword order. `fits_header.extract_headers()` reads `sensor.gain` as
`GAIN` first, `EGAIN` second — fine for a reported metadata field, but wrong here: on most CMOS
cameras `EGAIN` is the true e⁻/ADU conversion while `GAIN` holds the camera's own gain
*setting* in arbitrary vendor units (0–500 on a ZWO ASI). Threading that value through would
have divided the Poisson term by something like 120, understating the error by an order of
magnitude — considerably worse than the `gain=1` assumption it replaced. `_resolve_gain()`
therefore prefers `EGAIN`, and rejects any candidate outside a plausible e⁻/ADU range
(0.05–20) with a warning, falling back to 1.0. `config.PHOTOMETRY_GAIN_E_PER_ADU` is available
for a deployment whose capture software writes no usable `EGAIN`.

`sky_sigma` is deliberately left unconverted: it is the empirical per-pixel background scatter
measured off the frame's own ADU values, so it already carries read noise and sky shot noise
together in ADU.

### ✅ DONE — C8. One failing JPL Horizons ephemeris query can wipe out ALL anomalies for a frame

**Location:** `modules/anomaly_detector/_ephemeris_resolution.py:56-59`,
`modules/ephemeris.py:66-67`, `pipeline.py:851-865`

`ephemeris.query()` catches its own exceptions — fine. But
`asyncio.gather(..., return_exceptions=False)` gives no isolation between concurrent queries:
if any exception escapes the inner `except` (e.g. `asyncio.CancelledError`, which inherits from
`BaseException`, not `Exception`), it propagates out through `detect()`.
`pipeline.detect_anomalies_for_frame_data()` wraps the whole call in one `try/except` defaulting
`anomalies` to `[]` — that empty list is still posted, and `POST /frames/{id}/anomalies`
**replaces** the frame's entire anomaly set.

**Scenario:** a frame with several real anomalies (e.g. SUPERNOVA_CANDIDATE + ASTEROID); the
Horizons query for the asteroid hits a network failure exactly during task cancellation.

**Consequence:** every anomaly on that frame, including the unrelated SUPERNOVA_CANDIDATE, is
lost and replaced with an empty list; a re-run of `DETECT_ANOMALIES` even erases previously
stored anomalies in the DB. Separately, the fully synchronous `Horizons()` call has no timeout
and blocks the worker's whole event loop.

**Fix direction:** `return_exceptions=True` with per-item handling, plus an explicit
`asyncio.wait_for`/timeout around the Horizons call.

**Fixed** on all three levels the finding spans, since any one of them alone still leaves the
data loss reachable by another route:

1. `_resolve_ephemerides()` now gathers with `return_exceptions=True` and turns a returned
   exception into `ephemeris=None` for that one anomaly. A failed lookup costs that anomaly its
   ephemeris and nothing else.
2. `ephemeris.query()` runs the blocking `Horizons.ephemerides()` call via `asyncio.to_thread()`
   under `asyncio.wait_for(config.EPHEMERIS_TIMEOUT_SEC)` (new setting, default 30s). This also
   fixes the second half of the finding — run inline, that call blocked the worker's whole event
   loop and made the `asyncio.gather()` above concurrent in name only. A timeout returns `None`
   like any other failure. The abandoned thread is harmless: it holds nothing but its own HTTP
   socket, and a thread cannot be cancelled in any case.
3. Most importantly, `pipeline.detect_anomalies_for_frame_data()` no longer posts at all unless
   classification actually ran to completion. `POST /frames/{id}/anomalies` replaces the frame's
   whole anomaly set, so `[]` is only a meaningful payload when detection genuinely found nothing
   — which is still posted, so a frame whose anomalies were resolved away is cleared properly.
   This also covers the `anomaly_detector is None` path, which had the same destructive effect on
   a re-analysis.

Note that (3) is what actually closes the finding: (1) and (2) narrow the ways detection can
fail, but any *other* failure inside `detect()` reached the same empty-replace. Cancellation is
handled correctly by construction — `CancelledError` is a `BaseException`, so it propagates past
`pipeline.py`'s `except Exception` and nothing is posted.

### ✅ DONE — C9. `obs_time` is exposure-start, never exposure-midpoint corrected — used as-is everywhere a moving object's position is computed

**Location:** `modules/fits_header.py:147-154` → `catalog_matcher/_mpc.py:47`,
`forced_photometry.py:361-365`, `modules/ephemeris.py:56`

`DATE-OBS` is the shutter-open time per FITS convention, not the exposure midpoint. Nowhere is
`EXPTIME/2` added before this is passed to the SkyBot cone search, JPL Horizons, or Gaia
proper-motion propagation in forced photometry.

**Scenario:** a fast/close NEO on a long exposure (minutes) at 20-30"/min — the midpoint offset
alone reaches tens of arcsec, a meaningful fraction of `MOVING_CONE_ARCSEC=120"`.

**Consequence:** a systematic (not random) offset between the predicted and the actual detected
centroid — in mild cases just a less precise position; in extreme cases MPC matching fails
outright → loss of `ASTEROID`/`COMET` classification and ephemeris.

**Fix direction:** add `EXPTIME/2` to `obs_time` before any query that computes a moving
object's position.

**Fixed** as directed, but as a **separate** `obs_time_mid` field rather than a correction
applied to `obs_time` itself. `obs_time` is not only an input to those queries: it is what the
frame is registered under (`POST /frames`) and what `normalizer.py` builds the filename's
DateTime field from. Shifting it would have changed archived filenames and the stored
`DATE-OBS` semantic for every frame — a much larger blast radius than the finding calls for.

`fits_header.midpoint_time()` (public, so the standalone path can reuse it) computes
`obs_time + EXPTIME/2`, and `extract_headers()` returns it as `obs_time_mid`. Exactly the three
consumers that compute a position read it:

* the MPC/SkyBot cone search in `_match.py` — and only it; Simbad/Gaia/2MASS/Pan-STARRS are
  stationary on this timescale. `pipeline.py`'s step-9.5 `get_mpc_objects()` call had to move to
  the same value too: the epoch is part of the SkyBot cache key, so querying it with the start
  time would have turned that accessor's intended cache hit into a second network round trip
  against a different epoch;
* JPL Horizons, via `_detect.py` → `_resolve_ephemerides()`. Anomaly detection's own
  history/coverage queries deliberately keep `obs_time` — that bound is about when the frame was
  taken, not where anything was;
* forced photometry's Gaia proper-motion propagation (negligible at these timescales, but
  consistency costs nothing and the MPC positions it is handed are now at the midpoint).

Each falls back to `obs_time` when no midpoint exists (no `EXPTIME`, unparseable timestamp), so
a header-poor frame behaves exactly as before. The standalone `DETECT_ANOMALIES` path has no
local FITS access and recomputes the midpoint from the stored frame record instead, via
`pipeline._frame_exptime()`, which tolerates both the flattened and the nested
`observation.exptime` shape the API can return.

### ✅ DONE — C10. DATE-OBS and TIME-OBS are never combined

**Location:** `modules/fits_header.py:147-154`

The code takes the first non-empty key on an either/or basis: `DATE-OBS`, else `TIME-OBS`, else
a value derived from `MJD-OBS`. The older FITS convention stores only the date in `DATE-OBS`,
with time-of-day separately in `TIME-OBS`.

**Scenario:** capture software writing `DATE-OBS` in the old date-only form plus a separate
`TIME-OBS` — the time-of-day is dropped entirely (effectively midnight). If only `TIME-OBS` is
present, `obs_time` becomes a bare time string with no date.

**Consequence:** an hours-scale (not seconds-scale) epoch error for SkyBot/Horizons queries and
anomaly-history comparisons, or a downstream `Time(obs_time)` parse failure.

**Fix direction:** combine `DATE-OBS` (date) with `TIME-OBS` (time) when both are present and
`DATE-OBS` carries no time component.

**Fixed** as directed, in a new `_resolve_obs_time()` that considers the three keywords together
rather than taking the first non-empty one. In order: a `DATE-OBS` that already carries a time
of day is used as-is; a date-only `DATE-OBS` is combined with `TIME-OBS`; `MJD-OBS` is converted;
otherwise `None`.

Two additions beyond the direction as written:

* A `TIME-OBS` that is itself a full timestamp (some capture software writes one there) is
  preferred over splicing it onto `DATE-OBS`, since splicing would then produce a doubled date.
* The finding's second case — `TIME-OBS` alone — now yields `None` instead of a bare
  time-of-day string. Nothing downstream can parse `"22:01:34"`, so returning it only converts
  a missing timestamp into a corrupt one; `MJD-OBS` is tried first, and the dead end is logged.

A date-only frame with no `TIME-OBS` at all still resolves to midnight — there is nothing else
to use — but now says so at WARNING rather than silently. A pre-1997 `DD/MM/YY` date is still
not recognized as a date and passes through unchanged, as before.

### ✅ DONE — C11. FWHM/elongation medians that gate BLUR/TRAIL are computed on unfiltered raw detections, not the star mask

**Location:** `modules/qc.py:351-384` (medians) vs. `387-434` (star mask, used only for
`star_count`)

`fwhm_median`/`elongation_median` are computed over **all** raw sep detections, including
extended/non-stellar objects (nebula clumps, galaxies) not caught by the streak mask (which
only rejects very elongated/long features, not moderately elongated structures). The star mask
filtered by elongation/FWHM/flux is computed right after but used only for `star_count`.

**Scenario:** a narrowband nebula frame — among the few detections, filament clumps with high
elongation and inflated FWHM appear. This is worse for narrowband frames because they're
allowed a smaller sample (`QC_STARS_MIN_NARROWBAND=5`), where the median is highly sensitive to
one or two outliers.

**Consequence:** a technically well-focused, well-tracked frame can get a false `BLUR`/`TRAIL`
reject purely from the target's own morphology. The same skewed estimate is then passed
downstream as `psf_fwhm_arcsec` to `astrometry.solve()`/`subtraction.run()`.

**Fix direction:** compute `fwhm_median`/`elongation_median` over the same star mask already
computed for `star_count`.

**Fixed**, but *not* over that mask — doing literally this would have made both flags dead
branches. The star mask cuts at `STAR_FWHM_MAX_ARCSEC` and `STAR_ELONGATION_MAX`, whose defaults
(8.0″, 1.5) sit at or below `QC_FWHM_MAX_ARCSEC` (8.0″) and `QC_ELONGATION_MAX` (2.0). A median
taken over its survivors can never exceed either QC threshold, so `BLUR` and `TRAIL` would both
become unreachable — the same cut-below-the-threshold-being-tested failure as C2.

Each median is instead filtered on the axis it does **not** measure:

* `fwhm_median` over **round** sources (`elongation < STAR_ELONGATION_MAX`) — filaments, edge-on
  galaxies and streak remnants go; every blurred star stays, however blurred.
* `elongation_median` over **compact** sources (`fwhm ≤ STAR_FWHM_MAX_ARCSEC`) — nebula clumps
  and galaxies go; a trailed star's FWHM only grows as `sqrt((e²+1)/2)`, so it stays inside that
  bound across the elongation range `TRAIL` actually discriminates.

A roundness cut cannot remove a *round* extended object (face-on galaxy, round nebula knot), and
no absolute FWHM bound can either without capping the quantity `BLUR` tests. So the FWHM subset
gets one more, purely **relative** pass (`_clip_broad_outliers()`): anything broader than 1.5× the
lower quartile of that subset's own FWHM distribution is dropped. The factor is the same
stellar-PSF tolerance `modules/astrometry/_extraction.py` already applies around its own
`psf_fwhm_arcsec`. Being relative, a uniformly blurred frame shifts the quartile up with
everything else and nothing is clipped, so `BLUR` remains reachable at any blur level. The
elongation subset needs no counterpart: what contaminates it is extended morphology, already
removed by the compactness cut, and a relative clip on elongation itself would start eating into
the uniformly-trailed case `TRAIL` exists to catch.

Both subsets keep one absolute cut, `STAR_FWHM_MIN_ARCSEC`, which drops hot/warm pixel clusters;
a floor can only bias the estimate upward, so it cannot hide blur. A subset of fewer than 3
sources is not a population, and the raw all-detections median is used instead — which is also
what keeps both flags reachable on a frame blurred or trailed badly enough that its own stars
fall outside the opposite axis' bound and empty the subset out.

This also cleans up the downstream `psf_fwhm_arcsec` handed to `astrometry.solve()` and
`subtraction.run()`, which was skewed by the same contamination.

### ✅ DONE — C12. `_move_rejected()` silently overwrites an existing rejected file

**Location:** `modules/qc.py:623-654`

`shutil.move(fits_path, dest_path)` with no `os.path.exists(dest_path)` check. On POSIX this
silently overwrites an existing file of the same name under
`/fits/rejected/{object}/{FLAG}_{filename}`.

**Scenario:** a re-run against the same original filename, a test retry, or a normalized-name
collision (see M11 below, Flat frames).

**Consequence:** outright destruction of a previously rejected file — in the one subsystem
whose entire purpose, per CLAUDE.md, is "allows manual review if needed".

**Fix direction:** check for an existing destination and append a suffix/timestamp on
collision instead of silently overwriting.

**Fixed** as directed. `_unique_destination()` counts up a numeric suffix before the extension
(`BLUR_frame.fits` → `BLUR_frame_1.fits` → `_2` …) and the collision is logged at WARNING with
both names, so the operator can see that two rejections share an original filename rather than
silently finding only the later one.

A counter was chosen over a timestamp because the names stay readable and sort in rejection
order; the timestamp survives only as the fallback past 1000 suffixes, which exists purely to
keep a bounded probe from becoming an unbounded one. The probe is not atomic, but the pipeline
has a single writer per file and the fallback terminates regardless.

## High-priority findings

### ✅ DONE — H1. Gaia proper motion is ignored in ordinary catalog matching and in the WCS-offset vote accumulator (only applied in forced photometry)

**Location:** `modules/catalog_matcher/_gaia.py:123-163`, `_wcs_offset.py:43-50, 127-137`

`_match_gaia()` and the vote-accumulator input build coordinates from raw Gaia DR3 `ra/dec`
(epoch J2016.0), without `pmra`/`pmdec`. Over 10 years (2016→2026) a high-proper-motion star
(hundreds of mas/yr) drifts several arcsec — comparable to `MATCH_CONE_ARCSEC=5"`.

**Consequence:** such a star fails to match at the Gaia stage, ends up `catalog_name=None`,
satisfies the "shifted" condition, and is falsely classified `MOVING_UNKNOWN`; it also poisons
the WCS-offset vote accumulator for every other source in the frame.

**Fixed.** `_gaia._propagate_to_epoch()` propagates every queried star from its own
`ref_epoch` to the frame's `obs_time` once, in `match()`, right after `_query_gaia()` — so
both consumers (the vote accumulator and `_match_gaia()`) see the corrected positions without
either needing a signature change. `obs_time` (shutter-open) is used rather than
`obs_time_mid`: a half-exposure is several orders of magnitude below the year-scale baseline
this correction works on.

Two properties were deliberate. The star dicts are **copied**, not mutated — `_query_gaia()`
returns the cached list itself, and the same sky region is routinely re-used by frames from
other epochs within `CACHE_TTL_HOURS`, so an in-place shift would write one frame's epoch into
every later frame's catalog. And a star with no astrometric proper-motion solution
(`pmra`/`pmdec` `None`), an unparseable `obs_time`, or a position at the pole keeps its catalog
position, degrading to exactly the previous behaviour instead of failing the stage.

`get_gaia_stars()` is left un-propagated on purpose: `modules/forced_photometry.py`, its only
caller, applies the identical correction itself before projecting to a pixel, and propagating
in both places would apply the shift twice.

### ✅ DONE — H2. Simbad query radius doesn't cover the frame corners

**Location:** `modules/catalog_matcher/_simbad.py:39`

`radius = fov_deg / 2.0` — the only catalog without the `√2` factor (Gaia/2MASS/Pan-STARRS use
`fov_deg·√2/2` to cover the full diagonal). The corner region of a rectangular frame
(~29% of its area) is never queried against Simbad.

**Consequence:** a named Simbad object (variable, binary, galaxy) in a frame corner is missed,
falls back to Gaia's generic `object_type="STAR"`, and permanently loses the ability to trigger
`VARIABLE_STAR`/`BINARY_STAR`/`SUPERNOVA_CANDIDATE` (compounds C1).

**Fixed.** `_simbad._query_simbad()` now uses `fov_deg × sqrt(2)/2`, matching the other three
sky-position catalogs exactly. The over-fetch outside the frame is the same one they already
accept: matching is positional and `MATCH_CONE_ARCSEC`-bounded, so an object beyond the frame
edge simply never matches anything. The cache key is unchanged (it keys on `fov_deg`, not on
the derived radius), so an entry written before this change expires normally within
`CACHE_TTL_HOURS` rather than pinning the old, narrower result set.

### ✅ DONE — H3. MOVING_UNKNOWN is unreachable for objects that shift by more than `MOVING_CONE_ARCSEC` between frames

**Location:** `modules/anomaly_detector/_classify.py:138`, `_movement.py:40-82`

`wide_history` is searched with radius `MOVING_CONE_ARCSEC` (120") around the **current**
position. If an object moved more than 120" relative to the previous frame, its old position is
physically outside the search radius — "shifted" is never confirmed.

**Consequence:** a fast mover falls through to generic `UNKNOWN` (no track chart, no
ephemeris), or, if the area isn't covered yet, to `FIRST_OBSERVATION` — dropped entirely.

**Fixed.** The wide cone is now sized per candidate rather than once for the whole search:
`_movement._find_wide_history()` tests every historical detection against
`_wide_cone_radius_arcsec()`, which keeps `MOVING_CONE_ARCSEC` as a floor and extends it to
`MOVING_RATE_ARCSEC_PER_MIN × elapsed minutes`. How far an object can legitimately have moved
between two frames is a rate times a time gap, not a constant.

Two new bounds keep that from simply re-introducing the false-positive mode the second half of
the "shifted" evidence exists to prevent — a cone's risk grows with its area, since every extra
historical detection swept in is another candidate for the "its old position has vacated" test:
`MOVING_CONE_MAX_ARCSEC` (600″) caps the radius, and `MOVING_EXTEND_MAX_GAP_MIN` (30 min)
declines to extend at all for an older detection. Past that gap `rate × time` exceeds the cap
for any plausible rate, so the extension would degenerate into "the cap, always" — a permanently
wide cone — and a gap that long is a different session anyway, where pairing "something left A"
with "something appeared at B" carries little weight. `MOVING_RATE_ARCSEC_PER_MIN` defaults to
30″/min, the fast-NEO regime; anything faster trails within a single exposure and is already
caught by the `SPACE_DEBRIS` branch on elongation alone, which needs no previous position at all.

Either timestamp missing or unparseable falls back to the plain `MOVING_CONE_ARCSEC`, i.e. the
previous behaviour. `_prefetch.py`'s batch radius grew to `MOVING_CONE_MAX_ARCSEC + 400″`, since
a candidate the API never returned cannot be filtered back in client-side, and the anomaly's
`notes` now report the radius actually applied rather than the constant.

### ✅ DONE — H4. Filename-based object-name fallback breaks on names starting with a digit

**Location:** `modules/normalizer.py:128-134`

The loop stops at the first numeric token, treating it as the exposure time. But numbered
asteroids ("4_Vesta", "433_Eros") and stars ("61_Cygni") themselves start with a number.

**Consequence:** if the `OBJECT` header is empty, the frame archives to
`/fits/archive/_UNKNOWN/` instead of its real object directory — breaking history continuity
for subtraction (`SUBTRACTION_MIN_FRAMES` for that object never accumulates).

**Fixed.** The pure-digit rule no longer applies to a leading segment that is immediately
followed by one starting with a letter — the whole shape of a numbered designation
(`4_Vesta`, `433_Eros`, `61_Cygni`). An exposure time is never the leading token in any
convention this pipeline has seen, so nothing is given up.

The "starts with a letter" test is deliberately stricter than "contains a letter": a normalized
timestamp segment (`2024-03-15T22-01-34`) contains one, so the looser test would have made a
filename that genuinely does lead with an exposure time swallow the timestamp as an object
name. Such a filename still falls back to `_UNKNOWN`, as before.

### ✅ DONE — H5. No color-term correction in Gaia zero-point calibration for non-L filters

**Location:** `modules/photometry.py:114-167`

`zp = median(catalog_mag[Gaia G] − mag_instrumental)` is applied as a single constant equally
for L/U/B/V/R/I/SDSS filters. The difference between instrumental magnitude in R/B/V and Gaia G
is a function of stellar color (color term), not a constant.

**Consequence:** systematic bias in `mag_calibrated` that drifts night to night with the
reference-star color mix — can produce a false Δmag &gt; 0.5 mag simultaneously across many
stars in a single epoch.

**Fixed.** `_query_gaia()` now also returns each star's `bp_rp` (recomputed from
`phot_bp_mean_mag − phot_rp_mean_mag` when the precomputed column isn't in the returned table),
`_match_gaia()` carries it onto the matched source as `_catalog_color`, and
`_compute_zero_point()` fits `catalog_mag − mag_instrumental = zp + k × (BP−RP − color_ref)`
instead of taking a median, with three 3σ-clipped passes so one blended or variable reference
can't tilt the slope.

The zero point is reported **at** `color_ref` — the reference set's own median colour — rather
than at BP−RP = 0. That choice is what makes the result usable for the sources that actually
matter: an uncatalogued transient has no Gaia entry and therefore no colour, so it applies `zp`
bare, which amounts to assuming it has a typical colour for this field. That assumption is worth
what `k` can move across the field's own colour spread, so it is folded into `mag_err`
(`|k| × color_scatter`) rather than left silent. A source whose colour *is* known gets the exact
transformation.

Three guards keep a bad fit from being worse than no fit, each falling back to the plain median
— i.e. the previous behaviour exactly: fewer than `PHOTOMETRY_COLOR_TERM_MIN_REFS` (10)
coloured references, a colour span below `PHOTOMETRY_COLOR_TERM_MIN_SPAN` (0.5 mag, since a
slope fitted over a single-colour field is unconstrained and extrapolating it is worse than not
correcting), or a fitted `|k|` above `PHOTOMETRY_COLOR_TERM_MAX` (1.5 mag/mag, physically
implausible for a broadband filter against G).

`modules/forced_photometry.py` was given the same treatment rather than left on the constant
offset — it is exactly where the faint Gaia recoveries land, and it already has each star's
colour to hand. `pipeline.py` reads the solution off a measured source
(`_color_term`/`_color_ref`/`_color_scatter`) the same way it already reads `zero_point`.

### ✅ DONE — H6. Zero-point references aren't screened for Gaia data-quality flags; MAD at n=3 understates error precisely when an outlier is present

**Location:** `modules/photometry.py:120-167`

`phot_variable_flag`/`duplicated_source`/`ruwe` are never checked — a variable or blended star
can silently enter the reference set. At the minimum n=3 with a "2 good + 1 outlier" set, the
median-absolute-deviation error estimate is systematically understated — exactly when
calibration is least reliable.

**Consequence:** silently wrong calibration with a falsely low `zero_point_err`.

**Fixed**, both halves separately.

*Screening.* `_query_gaia()` now also returns `ruwe`, `phot_variable_flag` and
`duplicated_source`; `_match_gaia()` carries them onto the matched source as `_catalog_flags`;
and `_is_usable_reference()` drops a catalogued variable, a `duplicated_source`, or anything
above `PHOTOMETRY_REF_MAX_RUWE` (1.4, the community-standard cut) from the reference set. A
flag the catalog didn't supply counts as acceptable, so a narrower astroquery column set keeps
calibrating exactly as before. Screening only narrows the set, and narrowing it below the 3
references a zero-point needs would cost the frame its calibration entirely — a worse outcome
than an imperfect zero-point — so that case falls back to the unscreened set with a warning.

*The n=3 MAD.* `_robust_scatter()` replaces the bare `1.4826 × MAD`. The concrete failure was
sharper than "understated": for a "two good plus one outlier" triple the median sits on one of
the two good values and the MAD is exactly **zero**, so the frame reported
`zero_point_err = 0.0`. Croux & Rousseeuw's finite-sample factor corrects the MAD's low bias at
small n, and below 6 references the result is floored by the consistency-scaled mean absolute
deviation, which cannot collapse unless every value is identical. With three references a single
outlier genuinely cannot be identified as one, so the honest estimate is the one that keeps its
influence rather than the one that discards it. Both corrections converge to the previous
behaviour as n grows, and the colour fit's own residual scatter uses the same helper.

### ✅ DONE — H7. No sigma-clipping in sky-annulus statistics

**Location:** `modules/photometry.py:430-431`, `modules/forced_photometry.py:152-153`

`ApertureStats(data_sub, annulus)` with no `sigma_clip` — a neighboring star, cosmic ray, or
(worst case) the host galaxy's own light — exactly the `SUPERNOVA_CANDIDATE` scenario —
directly biases the background median.

**Consequence:** systematically wrong photometry precisely in dense fields and near galaxies —
where it matters most.

**Fixed.** Both call sites pass `sigma_clip=SigmaClip(sigma=PHOTOMETRY_SKY_SIGMA_CLIP,
maxiters=5)`, via a `_sky_sigma_clip()` helper in each module (hand-duplicated, the convention
`forced_photometry.py` already follows for the rest of this module's photometry math). A
non-positive threshold returns `None` and restores the unclipped median exactly.

The clip is worth having even though the statistic taken is already a median: a median resists a
few contaminating pixels, but the contamination here is not a few pixels — a neighbour's wings or
a galaxy's disk fill a substantial fraction of the ring, which moves the median too. The test
covering this runs against real photutils rather than the mocked `ApertureStats`, so the fix is
shown to change the number and not merely to pass an argument through.

### ✅ DONE — H8. astroalign's footprint mask is discarded before stacking references

**Location:** `modules/subtraction.py:203`

`aligned, _ = astroalign.register(source, target)` — the second return value (mask of
extrapolated/invalid pixels after the geometric transform) is ignored.

**Consequence:** invalid edge pixels enter the median stack as ordinary data → false residuals
in the diff image, uncovered by the saturation, streak, or near_edge filters.

**Fixed.** `_align_frame()` returns `(aligned, footprint)` and `_median_reference()` takes the
per-pixel median over a masked array built from those footprints, so a value astroalign could
not fill from the source frame never counts as a measurement.

A pixel that **no** reference covered — the overlap shrinks with every frame added, and a
dithered sequence guarantees some such pixels — is given the new frame's own value, making the
difference there exactly zero. Detection cannot fire on zero, which is the point: leaving the
pixel at whatever the stack happened to hold is precisely the false residual being avoided.

A reference whose footprint is missing, or is not a usable boolean mask of the right shape,
counts as fully valid, and a stack where no reference supplied one takes the plain `np.median()`
path — so an astroalign version that returns something unexpected degrades to the previous
behaviour rather than losing subtraction.

### ✅ DONE — H9. `np.median` (not `nanmedian`) — one NaN in one reference can null subtraction for the whole frame

**Location:** `modules/subtraction.py:173-187, 950-951`

No NaN/Inf handling anywhere in the chain; `astroalign.register` can introduce NaN in
unprojected regions; `np.median()` doesn't ignore NaN.

**Consequence:** a single NaN pixel in one archived file (not rare — masked pixels from prior
calibration) can null the subtraction result for the entire new frame — silently zero
candidates.

**Fixed** by folding non-finite values into the same per-pixel mask H8's footprints go through,
rather than by switching to `np.nanmedian()`. The two exclusions are the same kind of statement
— "this reference has no measurement at this pixel" — so they belong in one mask, and a masked
median also gives an answer for the case `nanmedian` cannot: a pixel non-finite in *every*
reference, which `nanmedian` returns as NaN (with a warning) and which here takes the new frame's
own value, holding the difference at exactly zero.

The new frame's own non-finite pixels needed separate handling: no reference can repair them, and
left alone they reach `sep`, whose background/RMS estimate they corrupt for the whole frame —
the same class of damage as the original bug, from the other side. `run()` zeroes them in the
difference and ORs them into the detection mask the saturated vicinity already uses, making them
simply a place nothing can be found.

### ✅ DONE — H10. No quality/seeing filtering of subtraction reference frames — including now-archived QC-failed frames

**Location:** `modules/subtraction.py:68-132`

Reference selection is recency + optional PA-closeness only, never reading `fwhm_median`/
`quality_flag`. Since the recent pipeline change that archives QC-failed frames too (see
CLAUDE.md), the archive can now hold `BLUR`/`TRAIL` frames mixed with good ones.

**Consequence:** a blurred reference produces the classic ring-shaped residual at every star
after subtracting a sharp new frame (mismatched-PSF differencing) — systematic false
candidates plus reduced sensitivity to faint transients.

**Fixed**, but the interesting part was *where* the quality information could come from. The
pipeline has no database access and the API has no filesystem access, so neither side alone can
answer "what is the QC verdict on this file on disk?" for an arbitrary archived frame. The
frame's own header is the one place they meet: `pipeline.py`'s `_write_qc_headers()` stamps
`QCFLAG` and `QCFWHM` into it at archive time, right beside where `_write_solved_wcs()` already
bakes in the solved WCS, and `subtraction._screen_by_quality()` reads them back with a
header-only read per candidate — no pixel data, no network.

The screen drops any frame whose `QCFLAG` is not `OK`, and any whose `QCFWHM` exceeds the new
frame's own measured FWHM by more than `SUBTRACTION_REF_MAX_FWHM_RATIO` (1.5). `QCFWHM` is
written only when `qc.analyze()` reported the FWHM in arcsec — it can be a raw pixel count when
the frame's headers don't support a plate scale, and writing that under an arcsec-documented
keyword would have a later frame comparing two incompatible quantities.

Two fallbacks keep this from costing subtraction more than it saves: a frame carrying neither
keyword (archived before this existed, or placed there by hand) is kept, since it cannot be
judged either way; and if screening would leave fewer than `SUBTRACTION_MIN_FRAMES`, the
unscreened set is stacked with a warning that PSF-mismatch residuals are to be expected — the
same reasoning as H6's zero-point reference screen.

### ✅ DONE — H11. near_edge subtraction candidates are hard-rejected unconditionally, regardless of shape

**Location:** `modules/subtraction.py:449-465`

Unlike the main detector, where `near_edge` only raises the elongation bar, here **any**
near_edge subtraction candidate is dropped outright — including compact, point-like (non-coma)
detections.

**Consequence:** a real transient that happens to fall near the frame edge (e.g. from a
dithering pattern) can never be found via subtraction.

**Fixed.** The blanket rejection is replaced by the property that actually separates the two
populations. Coma and the other off-axis aberrations stretch a PSF into an arc, and it is the
*mismatch* between two such arcs that the median stack fails to cancel — so a residual is
elongated and usually weak. An edge candidate now survives only if it is both round
(`SUBTRACTION_EDGE_ELONGATION_MAX`, 1.3) and strong (`SUBTRACTION_EDGE_SNR_MIN`, 10). Both bars
are deliberately stricter than their whole-frame equivalents (`STAR_ELONGATION_MAX` allows 1.5
anywhere; detection itself only asks for `SUBTRACTION_DETECT_SIGMA`), because the edge zone is
where the false positives concentrate.

Fixing `subtraction.py` alone would have changed nothing observable: `_classify.py` suppressed
every `near_edge` source independently, so a recovered candidate would have been dropped one
step later. `_survives_edge_zone()` re-applies the identical test there — re-applies rather than
trusts, because the standalone `DETECT_ANOMALIES` path reconstructs its sources from the API and
may carry rows an earlier, looser revision of `subtraction.py` wrote. The exemption is scoped to
subtraction candidates: an ordinary detection's near-edge suppression rests on a different
mechanism (a coma-shifted centroid that made catalog matching miss), which shape cannot rule
out, and a subtraction candidate additionally carries pixel-level evidence that nothing was
there before.

### ✅ DONE — H12. Streak mask in subtraction is computed AFTER background/RMS estimation

**Location:** `modules/subtraction.py:384-395`

`sep.Background()`/`globalrms` are computed before the streak mask exists — a bright satellite
trail (below the saturation threshold) contributes to the background/RMS estimate.

**Consequence:** `SUBTRACTION_DETECT_SIGMA × rms` is inflated for the **whole** frame because
of one trail — reducing sensitivity to faint real transients elsewhere in the same frame.

**Fixed.** The ordering itself cannot be swapped — the streak mask is found by running a coarse
pass over an already-background-subtracted image, so a first background estimate has to exist
before the mask can. What was missing is the second pass: once the mask is in hand, the
background and RMS are re-measured with those pixels excluded, and it is that RMS the detection
threshold is scaled from.

`modules/astrometry/_extraction.py` had the identical ordering (the two modules keep
hand-duplicated copies of this pre-pass) and was fixed the same way, although the finding named
only `subtraction.py`. There the stake is a little higher still: the RMS is both the threshold's
scale *and* the denominator of every source's reported SNR, which `STAR_SNR_MIN` then filters on.

### ✅ DONE — H13. Subtraction candidate SNR formula ignores resampling-correlated noise

**Location:** `modules/subtraction.py:429`

`snr = flux / (rms * sqrt(npix))` assumes uncorrelated per-pixel noise. But the reference goes
through two interpolation passes (pre-rotate + astroalign), introducing spatial correlation —
the real number of independent degrees of freedom in the aperture is smaller than `npix`.

**Consequence:** systematically overstated candidate significance — false candidates with
"formally significant" but actually noise-driven SNR, especially after pre-rotation.

**Fixed** by measuring the correlation rather than assuming a value for it, since how much
there is depends on the interpolation each individual stack went through — the number of
resampling passes, the pre-rotation angle, the alignment transform. `_noise_correlation_factor()`
compares the difference image's own per-pixel scatter against the scatter of a box-averaged copy
of it: independent noise averaged over a box of side `k` falls as `1/k`, and whatever the real
image falls short of that is exactly the factor an aperture's noise needs. Both scatters are
MAD-derived so the real sources in the frame, which are not noise, don't set the answer.
Verified against synthetic white and smoothed noise of identical per-pixel RMS: 1.01 and 2.86.

The result divides every candidate's `snr` and is capped by `SUBTRACTION_NOISE_CORR_MAX` (4.0),
with 1.0 restoring the previous formula exactly; a measurement that fails, or comes out below 1,
also returns 1.0. This matters more now than it did before H11: that finding's edge-zone test
gates on `snr`, so an overstated significance would let coma residuals back through the very
bar built to keep them out.

### ✅ DONE — H14. Reference pre-rotation crops frame corners for non-90°/180° angles

**Location:** `modules/subtraction.py:591-655`

`scipy.ndimage.rotate(..., reshape=False, mode="constant", cval=0.0)`, gated at
`SUBTRACTION_PREROTATE_MIN_DEG=2°` — triggers at modest angles, not just 180° flips. A
same-canvas rotation mathematically crops corner content for any angle not a multiple of
90°/180°.

**Consequence:** on de-rotator-less mounts (alt-az, field rotation) a sharp zero/data boundary
creates a contrasting false residual, and lost corner stars can raise `astroalign`'s own
failure rate exactly for the large-angle cases pre-rotation is meant to help most.

**Fixed**, both consequences separately.

`reshape=True` lets the canvas grow instead of cropping, so no star is lost. That costs nothing
downstream: `astroalign` resamples onto the new frame's grid regardless of the source's shape,
which this module already relies on for references captured with a different camera.

The constant fill that necessarily remains is marked invalid rather than left as data. A
validity map is rotated by the same angle (`order=0`, so it stays binary), the reference goes to
`astroalign` as a `np.ma.masked_array`, and `propagate_mask=True` carries that marking through
its own resampling into the returned footprint — which `_median_reference()` (H8) already
excludes from the stack. Without that, the padded region would have been ordinary data holding a
constant, and every star the new frame has there would have differenced into a false transient.

### ✅ DONE — H15. No plausibility check on astap's WCS solution beyond string parsing + `has_celestial`

**Location:** `modules/astrometry/_wcs.py:83, 111-125`, `_astap.py:191-215`

Neither the number of matched stars, the solution residual/RMS (astap writes it into the
`.wcs` comment but nothing parses it), nor the sanity of `ra_center`/`fov_deg` is checked. This
is especially risky combined with `ASTAP_RETRY_WIDE_SEARCH` — a blind 30°-radius search is
statistically more prone to a false-positive star-pattern match.

**Consequence:** a false "solution" silently becomes a systematic position error for the whole
frame — no downstream module can detect it, since the WCS is treated as authoritative by
construction.

**Fixed** with structural checks rather than statistical ones. astap's residual and
matched-star count exist only in a free-text comment whose wording varies by version and search
mode, so gating on a parse of it would be a new failure mode of its own; that line is now logged
(`_log_astap_solve_report()`), which is what the finding's "nothing parses it" asked for, and the
gate is built on properties that hold regardless of solver version:

* reference coordinates on the sphere;
* a plate scale inside `ASTROMETRY_PIXEL_SCALE_MIN/MAX_ARCSEC` — this alone catches the
  2026-08-06 CD/PC double-scaling incident (0.78″/px read back as 0.0002″/px), which was
  previously noticed only because every FWHM collapsed to zero;
* a non-degenerate CD matrix, since a collapsed axis maps the whole frame onto a line;
* a finite, on-sphere pixel→world round trip at the frame centre.

A failure is hard — `solve()` returns `{}` — rather than a warning, because a confidently wrong
WCS is worse than no solve: the frame's sources would be posted at wrong coordinates and then
compared against history at those same wrong coordinates, seeding the error into the database.

Deliberately *not* added: rejecting a solve whose centre sits far from the mount's reported
RA/Dec. That is precisely the case `ASTAP_RETRY_WIDE_SEARCH` exists to rescue — the 2026-08-13
IC3322A incident was 24 genuinely mis-pointed frames — so it is surfaced as
`pointing_error_arcsec` (docs/API.md §1) rather than used as a rejection criterion.

### ✅ DONE — H16. Astrometry's streak masking runs on the raw frame and can erase a genuine single-exposure fast-object track before extraction ever sees it

**Location:** `modules/astrometry/_streak.py`, `config.py:172-174`

A 30" length threshold and 5.0 elongation threshold don't geometrically distinguish a
satellite/plane trail from a genuine fast NEO trailing within one exposure — exactly what
should become a `SPACE_DEBRIS` candidate.

**Consequence:** such an object is erased from the data before `sep.extract()` runs — it
enters neither `sources` nor `sources_all`; there is no second chance, since this frame isn't
re-analyzed from other data.

**Fixed** without touching the thresholds, because the finding is right that they cannot
separate the two cases — a satellite trail and a fast NEO's trail are the same shape, and a
length cut that told them apart would have to know the exposure time and the object's rate,
neither of which this pre-pass has.

What it can do is stop *deleting* the evidence. `_build_streak_mask()` now returns the features
it masked alongside the mask, and `_extraction.py` re-emits each as one detection at its own
centroid. The mask keeps doing its real job (a trail no longer fragments into several small round
"stars"), while the object itself reaches `catalog_matcher` — where the MPC cone search can
identify a known NEO at that position and give it an ephemeris — and `anomaly_detector`, whose
`SPACE_DEBRIS` branch classifies an unknown one on elongation alone.

The re-emitted detections join `sources_all` only: a trail is not a star and must never enter
the photometric reference set. They also bypass `SOURCES_ALL_ELONGATION_MAX`, which exists to
reject the degenerate `a/b` a near-zero minor axis produces, not a feature deliberately selected
for being elongated — a full-frame trail's ratio is far past 15.

### ✅ DONE — H17. `_write_solved_wcs` doesn't strip old CD/PC/CDELT keys before writing astap's solution

**Location:** `pipeline.py:1691-1699`

`WCS.to_header()` emits a PC+CDELT representation even when the source WCS came from a CD
matrix; `header.update()` doesn't remove pre-existing `CD1_1..CD2_2`. The archived file can end
up carrying both the old CD keys (mount-pointing) and the new PC+CDELT keys (astap) at once.

**Consequence:** reading this mixed WCS with a different client/astropy version has no
guaranteed behavior — the same class of problem `_read_wcs()` explicitly fixes on read, with no
symmetric protection on write.

**Fixed.** `_strip_wcs_representation()` clears every `CD`/`PC`/`CDELT`/`CROTA` card before the
solved WCS is written over them, so the archived file carries exactly one transform.

`CROTA1/2` is included although the finding doesn't name it: it is the pre-CD rotation
convention, and a stale copy of it alongside a fresh CD matrix is the same ambiguity in older
clothes.

This is the write-side counterpart to a defence `_read_wcs()` already had to grow: astropy
multiplied a file's coexisting PC and CDELT together and turned 0.78″/px into 0.0002″/px (real
incident, 2026-08-06). A file this pipeline archives should not need that defence from whoever
reads it next — `modules/finder_chart/` reads WCS straight back out of these headers, and so
would any external client.

### H18. A bare numeric RA header is always treated as decimal degrees — a real hours/degrees ambiguity

**Location:** `modules/fits_header.py:157-163`

If `RA` isn't a sexagesimal string but a plain number, the code unconditionally treats it as
decimal degrees. Some ASCOM-driven software reports decimal hours there (a ×15 factor).

**Consequence:** distorts the diagnostic `pointing_error_arcsec`; worse, this same RA seeds
astap's narrow search center — with wrong units, the narrow search reliably misses and every
such frame pays the full cost of a wide/blind search.

---

### H19. API retry exhaustion loses a frame's entire science payload with no automatic re-queue

**Location:** `api_client/sources.py`, `anomalies.py`, `pipeline.py` Steps 7 and 14

The `frames` record itself isn't lost — `POST /frames` already succeeded and the file is
archived. But once the 3-attempt retry on `POST /sources`/`/anomalies` is exhausted (5xx across
the backoff window), that run's entire source/anomaly list is lost permanently — no re-post
task, no "needs re-analysis" flag.

**Consequence:** at odds with "do not lose the frame" — what's actually lost is the
sources/anomalies, not the frame record; recovery requires a manual reprocess.
