---
name: feedback_module_to_package_split
description: Rules for splitting a large modules/*.py file into a modules/*/ package without breaking existing tests, distilled from doing this to api_client/client.py, modules/anomaly_detector.py, modules/catalog_matcher.py, and modules/astrometry.py
type: feedback
---

This project is incrementally splitting its largest single-file modules (originally `api_client/client.py` 1660 lines, `modules/anomaly_detector.py` 1090 lines, `modules/catalog_matcher.py` 1317 lines, `modules/astrometry.py` 732 lines) into packages: a directory of the same name, with `__init__.py` as the "main file" (pure re-export layer, no logic of its own) and each cohesive group of functions in its own file. Candidates still flat as of this writing: `modules/finder_chart.py`, `pipeline.py`. `api_client/` was done first as `api_client/client/` then collapsed one level further into `api_client/` directly (see `feedback_api_client_patterns.md`) — don't reintroduce that extra nesting for other modules either, always split directly into `modules/<name>/`, never `modules/<name>/<name>/`.

**Not every candidate has the same shape.** `api_client`/`anomaly_detector`/`catalog_matcher` were all "many independent functions crammed into one file" — splitting was pure relocation, zero new function boundaries. `astrometry.py` was the opposite: essentially one ~580-line procedure (`solve()`) with a handful of comment-delimited steps ("Step 1", "Step 2", ...) inside it. Splitting that kind of file means *extracting new functions* from a monolith, not just moving existing ones — check with the user before doing this (asked via AskUserQuestion, offered "full split" vs. "light split, just pull out the one genuinely separate helper" vs. "skip it") since it's a materially higher-risk change: get the parameter/return-value boundaries between extracted steps wrong and you've introduced a real bug, not just moved code. When the original function's own comments already delimit clean, mostly-one-directional data flow between steps (as `astrometry.solve()`'s did: WCS-read → frame-geometry → source-extraction, each step's inputs are a strict subset of the previous steps' outputs), promoting those comments into function boundaries is safe; also preserve the *original* exception-handling boundary exactly (astrometry.py wrapped steps 2–4 in one try/except with one generic log line — so the extracted step-functions must not each catch-and-log their own errors, or a single failure starts producing multiple log lines / a different final error message than before).

Five distinct compatibility rules to check before doing this, each catching a different kind of test breakage:

1. **Attribute-chain patches always survive the split for free.** `patch("modules.anomaly_detector.api_client.get_sources_near_batch", ...)` or `patch("modules.anomaly_detector.ephemeris.query", ...)` keep working with zero test changes, AS LONG AS the package's own `__init__.py` does `import api_client` / `from modules import ephemeris` itself (even if unused there) — `unittest.mock`'s string-target resolver needs `getattr(package, "api_client")` to succeed at the point right before the final attribute, and it doesn't matter which submodule inside the package actually performs `api_client.get_sources_near_batch(...)` at runtime, because that call is a two-step lookup (name → module object, then `.attr` on that shared singleton) and the patch mutates the attribute on the real shared module object. This is exactly the same trick already documented for `httpx` in `feedback_api_client_patterns.md`.

2. **Bare-name patches on a private helper do NOT survive the split.** `patch.object(package, "_foo_with_retry", ...)` (or the string-form equivalent) breaks once `_foo_with_retry` and its caller move into a submodule — the caller's `_foo_with_retry(...)` call is a single-step global-name lookup against ITS OWN submodule's `__globals__`, not the package's `__init__.py` namespace, regardless of what `__init__.py` re-exports. Fix: import the specific submodule in the test (`from api_client import sources as _sources_module`) and patch on that object instead. This bit `api_client/client.py`'s `_post_sources_with_retry`-style tests; it did NOT come up for `anomaly_detector` because none of its tests patch a private helper this way (they only use rule 1's attribute-chain form, or rule 3's direct-call form below).

3. **Direct calls to a private helper from a test need it re-exported.** `modules/anomaly_detector.py`'s tests call `ad._haversine_arcsec(...)`, `ad._is_position_shifted(...)`, etc. directly (unit-testing the helper itself, not mocking it) — this is plain `getattr(package, name)`, so it works as long as `__init__.py` imports that name from wherever it actually lives, underscore and all. Before splitting a module, grep the test file for `<module_alias>._` to find every such name and make sure the new `__init__.py` re-exports all of them, not just the "obviously public" ones.

4. **A bare-imported name used by an orchestrator that spans several new submodules needs the orchestrator itself to switch to qualified access.** `modules/catalog_matcher.py`'s `match()` called `_query_gaia()`/`_query_simbad()`/`_query_mpc()`/etc. as bare names, and each of those bodies referenced `Gaia`/`Simbad` (from `from astroquery.gaia import Gaia`) as a bare name too — tests patched both styles directly on the package (`patch("modules.catalog_matcher.Gaia", ...)`, `patch("modules.catalog_matcher._query_mpc", ...)`). Splitting each catalog into its own file (`_gaia.py`, `_simbad.py`, `_mpc.py`, ...) turns EVERY one of those into rule 2's problem at once, because `match()` (wherever it ends up living) and each catalog's own query function are now unavoidably in different files. Fixing this by updating just the test's patch STRING (rule 2's usual fix) is not enough here, because the orchestrator's own bare `_query_gaia(...)` call would still resolve to whatever it imported at its own file's import time, bypassing a patch applied to `_gaia.py`. The actual fix has two parts: (a) have the orchestrator import each catalog as a submodule (`from . import _gaia, _simbad, _mpc`) and call through it (`_gaia._query_gaia(...)`, not a bare `_query_gaia(...)`) — turning every one of these into rule 1's safe attribute-chain form — and (b) update every test patch string to target the catalog's own submodule (`patch("modules.catalog_matcher._gaia.Gaia", ...)`, `patch("modules.catalog_matcher._mpc._query_mpc", ...)`). Do this whenever one orchestrator function fans out to N sibling implementations that tests mock individually — it generalizes well beyond catalog_matcher.

5. **A bare-imported CLASS used in only ONE extracted step is just rule 2's usual fix, no qualified-access rewrite needed.** `astrometry.py`'s `WCS` (`from astropy.wcs import WCS`) is only ever constructed in one place, the "read WCS" step — unlike rule 4's `Gaia`/`Simbad` (used inside a multi-catalog orchestrator fan-out), there's only one call site, so the fix is the plain rule-2 one: move `WCS`'s construction into its own file (`_wcs.py`) and update the test's patch string (`patch("modules.astrometry.WCS", ...)` → `patch("modules.astrometry._wcs.WCS", ...)`). Don't reach for rule 4's qualified-submodule-access machinery unless the same bare name is actually constructed from more than one extracted file — that's what makes rule 4 necessary, not the mere fact that a class is bare-imported.

**How to apply:** Before splitting any module, run `grep -n "patch(\|patch\.object(\|<alias>\._" tests/test_<module>.py` to classify every mock/direct-call site into one of the rules above, and design `__init__.py`'s imports/re-exports accordingly. After splitting, run the full suite (`python3.11 -m pytest tests/ -q` — NOT plain `python3`, which is often a stray 3.9 on this machine and produces unrelated `TypeError`/collection errors from `X | Y` runtime type syntax) and diff the failing-test list against a clean-stash baseline (`git stash -u`, not plain `git stash`, since untracked new package directories survive a plain stash and silently shadow the restored flat file via Python's package-over-module precedence — this produced a very confusing false "10 tests fixed by my refactor" result once).
